Redis is an in-memory database that persists on disk. The data model is key-value, but many different kinds of values are supported: Strings,

Transacciones
MULTI, EXEC and DISCARD are the foundation of transactions in Redis

El DISCARD es similar al ROLLBACK de SQL, pero lo que hace es no ejecutar la transacción, no vuelve los datos al estado anterior.
(transaction rollback vs. operation cancellation)

Listas

Las listas contienen múltiples valores ordenados que pueden actuar como colas (first in, first out) y como pilas (last in, first out). También
tienen acciones más sofisticadas para insertar en algún lugar en medio de una lista, restringir el tamaño de la lista y mover valores entre listas.

RPUSH
127.0.0.1:6379> RPUSH eric:wishlist 7wks gog prag
(integer) 3

LRANGE
127.0.0.1:6379> LRANGE eric:wishlist 0 -1
1) "7wks"

2) "gog"
3) "prag"

LREM
127.0.0.1:6379> LREM eric:wishlist 0 gog
(integer) 1

127.0.0.1:6379> LRANGE eric:wishlist 0 -1
1) "7wks"
2) "prag"

LPOP
127.0.0.1:6379> LPOP eric:wishlist
"7wks"
127.0.0.1:6379> LPOP eric:wishlist
"prag"
127.0.0.1:6379> LPOP eric:wishlist
(nil)

To act as a stack, after you RPUSH the values, you would RPOP from the end of the list
You can use LPUSH and RPOP to similar effect (a queue) or LPUSH and LPOP to be a stack.

Redis provides a single command for popping values from the tail of one list and pushing to the head of another. It’s called RPOPLPUSH (right
pop, left push).

127.0.0.1:6379> RPOPLPUSH eric:wishlist eric:visited
"prag"

Sorted Sets

===== PAGINA 14 =====

Los conjuntos ordenados de Redis son, al igual que los conjuntos de Redis, colecciones de cadenas que no se repiten. La diferencia es que
cada miembro de un conjunto ordenado está asociado con un score, que se utiliza para tomar el conjunto de manera ordenada, desde la
puntuación más pequeña a la más alta. Mientras que los miembros son únicos, las puntuaciones pueden repetirse.

Con los Sorted Sets se puede implementar una tabla de posiciones en un juego masivo en línea, donde cada vez que se envíe un nuevo
puntaje, lo actualizamos con ZADD y tomar los mejores jugadores con ZRANGE.

Volviendo a nuestro ejemplo, de las URLs, vamos a agregar tres elementos con sus valores (de score).

ZADD key [NX|XX] [CH] [INCR] score member [score member ...]

127.0.0.1:6379> ZADD visits 500 7wks 9 gog 9999 prag
(integer) 3

visits es la clave y después agregamos 3 elementos 'score member' al mismo tiempo.

Para incrementar un score de un elemento de este conjunto (usamos el ZINCRBY)

127.0.0.1:6379> ZINCRBY visits 1 prag
"10000"

Si queremos acceder a los primeros 2 elementos de este conjunto

127.0.0.1:6379> ZRANGE visits 0 1
1) "gog"
2) "7wks"

ZRANGE (de menor a mayor) y ZREVRANGE (REV = reverso)

127.0.0.1:6379> ZREVRANGE visits 0 -1 WITHSCORES

EXPIRE key seconds

Podemos crear un elemento y darle un tiempo de vida (time to live o TTL)

127.0.0.1:6379> SET ice "I'm melting..."
OK
127.0.0.1:6379> EXPIRE ice 10
(integer) 1
127.0.0.1:6379> EXISTS ice
(integer) 1
127.0.0.1:6379> EXISTS ice
(integer) 0

Antes de que 'ice' desaparezca, podemos preguntar cuánto le falta.

127.0.0.1:6379> TTL ice
(integer) 4

En cualquier momento, antes de que el dato expire, podemos anular el TTL usando PERSIST.

127.0.0.1:6379> PERSIST ice

Database Namespaces
0 → es la default.
Para cambiar de base, usar SELECT index.

En términos prácticos, las bases de datos de Redis se deben utilizar principalmente si es necesario separar diferentes claves que pertenecen
a la misma aplicación y no para usar una sola instancia de Redis para múltiples aplicaciones no relacionadas.

Cuando se usa Redis Cluster, el comando SELECT no se puede usar, ya que Redis Cluster solo admite la base de datos 0 (cero).

"hello"

Durability (o Persistencia)

Redis tiene algunas opciones de persistencia. En primer lugar tenemos la no persistencia, lo que simplemente mantendrá todos los valores
en la memoria principal.

Por otro lado, por default Redis graba (cada tanto) la información que tiene en memoria la persiste al disco cada tanto. Los valores por defaults
son los siguientes:

Seccion SAVE del redis.conf → http://download.redis.io/redis-stable/redis.conf

# save <seconds> <changes>

===== PAGINA 25 =====

save 900 1
save 300 10
save 60 10000

#   In the example below the behavior will be to save:
#   after 900 sec (15 min) if at least 1 key changed
#   after 300 sec (5 min) if at least 10 keys changed
#   after 60 sec if at least 10.000 keys changed

Si queremos obligarlo a grabar los datos, tenemos 2 comandos (SAVE y BGSAVE)

SAVE
Nunca deberías llamar al SAVE en un entorno de producción, porque bloquearía a los otros clientes, es mejor usar el BGSAVE (background
save)



Seguridad
https://redis.io/topics/security

Although Redis is not natively built to be a fully secure server, you may run across the requirepass setting and AUTH command in the Redis
documentation.

These can be safely ignored because they are merely a scheme for setting a plaintext password. Because a client can try nearly 100,000
passwords a second, it’s almost a moot point, beyond the fact that plaintext passwords are inherently unsafe anyway. If you want Redis
security, you’re better off with a good firewall and SSH security.
